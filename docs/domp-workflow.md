# 微信 SQL 数据运维完整流程

目标群的文本和文件监听先检查该群的启用状态、消息类型和各类型发送人名单，再读取完整内容、分析用途和风险、调用 MCP 完整流程、在原群 @ 原发送人回复。自己发出的消息和未在名单中的人员不触发工具。

发送示例：文本开头写 `需求 40386` 或 `xzsb-40386`，后面附完整 SQL；也可发送 `需求40386.txt`，文件内容为完整 SQL，多条语句用分号分隔。不能从 SQL 主键猜需求编号。支持 UTF-8（含 BOM）、GB18030、UTF-16（带 BOM）；过大、无法解码或超过完整分析长度的文件会回复失败原因，不会截断后执行。

SQL Skill 的“调用 MCP 工具”启用，连接保持原来的数据运维连接，工具使用“数据运维填报审核执行完整流程”（`process_data_maintenance`）。配置的提示词见 `backend/domp_bridge.py` 中的 `PROMPT`。程序自行生成原文参数和稳定消息标识，工具路由不由模型修改；模型输出用途和风险，高风险/未知/低置信度停止。实际 SQL 结构与系统申请脚本还会在 MCP 端核对。

已有群可运行以下命令更新现有 SQL Skills；保留原发送人名单、启用状态和连接，只取消 @ 机器人触发限制并更换提示词和完整流程工具：

```powershell
backend\.venv\Scripts\python.exe scripts\configure_domp_skill.py --owner "登录账号wxid" --chat "目标群id@chatroom"
```

原配置备份到 `backend/.sqlite_cache/domp_skill_before_时间.json`。文本和文件发送人名单独立，以页面现有配置为准。MCP 地址保持 `http://127.0.0.1:8765/mcp`，完整流程超时设置为 600 秒；数据运维助手必须运行且三个角色连接配置齐全。

返回需求编号、用途、风险、填报/审核/执行状态、逐条影响条数、合计、耗时和异常。0 保留、未知明确写“未知”，不使用分析回复冒充成功。长异常分段按顺序 @ 发送人回复。超时回复流程标识，使用查询接口核对，不能重新创建请求绕过防重。

页面 Skill 测试没有生产消息上下文，强制 `dry_run=true`，只分析不填报、审核、执行，也不发送微信。真实消息的业务写入由目标群和发送人名单授权；模拟测试均替换 MCP 和微信发送接口。

## 数据运维查询 Agent

目标群另有文本 Skill“任务与数据运维查询 Agent”，提示词为 `backend/domp_query_bridge.py` 的 `QUERY_PROMPT`。页面配置工具保留 `query_data_maintenance` 作为查询 Agent 标识，实际 MCP 路由由程序限定在三个只读工具中：

- “查一下 41198 任务处理情况”“查一下 41198 处理情况”“xzsb-41198 谁在处理”：调用 `query_operation_ticket`，对应桌面“查询 → 综合查询”，返回旧系统当前状态、受理人、机构、处理履历和评论；转现场处理不代表已解决，履历受理标记为“未”时显示尚未受理。
- “帮我查一下 41123 执行情况”“41233 执行了吗，结果如何”“41233 执行了吗”“41178 影响多少条”“目前有所少待审核的需求”“现在有哪些待执行需求”：调用 `query_data_maintenance`，返回真实 SQL 执行状态、逐条影响条数、合计、耗时、完整异常，或当前待办数量与前 20 条清单。执行成功且明细完整、无异常时回复“异常详情：无”；执行失败但系统没有异常文本时明确说明未返回，未取得完整结果时异常为未知。
- “41184 的执行详情发我看看”“把41184执行详情给我”“41184 SQL脚本发我看看”：仍调用只读 `query_data_maintenance`，在结果摘要中附逐条服务器 SQL 原文，不改写或再次执行。执行查询后接“详情呢/明细/SQL脚本呢”也可展示原文；会话仅保存不含 SQL 的结果摘要，长 SQL/异常按顺序分段 @ 原发送人，每段保留结果标记以防回调循环。
- “当前有多少待处理的任务”“今天分配了多少任务”“今天分配的任务详情”：调用 `query_task_processing`。待处理数量从新业务会话读取当前待处理清单，自动处理保持运行；今日分配来自本助手确认成功提交的 SQLite 持久化记录。回复包含编号、摘要、分配时间、指派人员、命中规则和真实结果，并说明启用时间及未保留历史/其他账号手工分配不在统计内。每页 20 条，可接“详情呢”“下一页”，翻页只承接同一发送人的已验证页码。

AI 识别意图，程序核对原消息编号；旧系统处理情况措辞强制走综合查询，不能误查 SQL 执行系统。未找到说明账号可见范围，同名多条需人工选择，读取失败不能冒充未找到或 0。查询不会启动自动派发或修改业务。

原文本名单中的人员可查询，机器人登录账号的本人也可在该群直接发送查询。本人查询使用隔离路径，只含查询 Agent，不能进入 SQL 填报审核执行流程；SQL 授权名单不变。机器人结果每段带“数据运维查询结果”标记，回调不会再次触发，防止循环回复。普通聊天和 SQL 原文不会进入查询 Agent。

更新已有群并加入查询 Agent：`backend\.venv\Scripts\python.exe scripts\configure_domp_skill.py --owner "登录账号wxid" --chat "目标群id@chatroom" --add-query-agent`。原配置先备份，重复运行复用现有查询 Skill。查询 Skill 测试可真实读取 MCP，只读且不发送微信。

## 查询会话上下文

会话以“机器人登录微信账号 + 群聊/私聊 ID + 发送人微信 ID”隔离。同一人在不同群有独立会话，同一群内不同人不会继承彼此的单号；昵称变化不影响会话。每个会话从创建时起最多七天，持续聊天也不延长，到期清除旧上下文并在下一次明确查询时生成新 session_id。SQLite 表 `query_conversations` 保存最近十二轮已验证查询（每轮原问题和答复摘要各最多 1500 字），后端重启后仍可承接有效会话；不把整个群聊、TXT SQL 原文或完整需求中的个人信息当作上下文。

例如“有哪些待审批”后接“待执行呢”会重新查询当前待执行清单；“查41198任务处理情况”后接“那41199呢”会改查41199；“它的执行结果呢”沿用最近一轮明确编号。明确的新编号/类型优先，上一轮是数量查询时不猜单号；没有有效上下文时提示补充。明确 SQL 流程的结果只记录编号和结果摘要，也可接着查询执行结果，后续问题不会复用旧 SQL 进行业务修改。模型收到同一发送人的历史查询数据，所有状态/数量仍从当前 MCP 结果生成。

同一人的消息按接收顺序串行处理，其他人可并行查询。查询回复允许紧接着问和重复同样问法；重复回调仍按消息 ID 去重，机器人结果标记继续阻止循环。页面 Skill 测试不绑定生产会话。

## 已有审批单据执行 Agent

另有“数据运维执行 Agent”（`execute_data_maintenance`），提示词在 `backend/domp_execution_bridge.py`。目标群原文本名单人员及登录账号本人可明确要求执行已有审批通过单据，本人使用只包含这个 Agent 的隔离路径，不进入 SQL 填报 Skill。可说“执行 41184”，或在同一发送人的上一轮待执行查询仅一条时说“执行下并告诉我结果”。程序保存最多 20 个已验证稳定编号；旧会话只认可程序标准答复里明确的一条工作编号，绝不拿最新清单中的另一条替代。清单为零/多条、会话过期、同名多条或目标不明时要求指定编号。执行结果提问仍走只读 Agent。

支持带称呼、@昵称及礼貌前缀的明确请求，例如“兄弟，帮我执行下 41184”“老师，麻烦把数据运维单 41184 执行一下”。入口按请求语句匹配而非要求整条消息以“执行”开头，登录账号本人也能进入隔离执行路径；否定、转述、未来计划及“执行了吗/帮我查执行结果”等只读问法不会发起执行。AI 确认动作，程序仍从当前原文核对唯一编号。

执行前重新调用只读待执行清单，核对稳定 work_id、work_num 和审批状态；MCP 服务继续检查服务器内实际申请 SQL 的风险和持久化防重记录，仅允许执行一次。目标已移出清单只读取原单结果，不执行其他单据。响应异常只读核对结果，不重发执行。返回真实逐语句成功/失败、0 或未知影响条数、合计、耗时及完整异常，所有段在原群 @ 发送人，结果标记防止回调循环。页面 Skill 测试只定位单据，不执行或发送微信。

配置更新命令追加 `--add-query-agent --add-execution-agent`，重复运行复用现有 Skills，保留发送人名单和连接。自动分配记录文件为数据运维助手目录中的 `task_assignments.local.sqlite3`，恢复旧运行日志只导入有真实成功提交时间的记录。
