# 微信 SQL 数据运维完整流程

## 填报失败后的编号区划选择

完整 SQL 流程因行政区划不唯一或找不到区划而停止、且确认尚未创建申请时，程序在原群 @ 原发送人，发送“请选择城市”及逐行编号的系统区划选项。例如 `1. 日喀则市`、`2. 日喀则市.日喀则市市本级`、`3. 日喀则市.桑珠孜区`。原发送人回复 `@Aixed 3`（当前登录账号的实际昵称）后，程序重新核对该名称和编码，直接按所选区划填报、审核、执行，无需再次回复“是”。可回复 `@Aixed 取消` 结束等待；文件传输助手中仍使用 `@空气`。

编号、选项、原 SQL 和原 request_id 保存到 SQLite，按登录账号、聊天和原发送人隔离，24 小时有效，重启后可继续。其他人回复、未正确艾特、无效编号、区划编码变更均不会触发填报。已发起业务请求但结果不明时只提示查询，不按另一个数字重复提交。五位旧单及补充批次保留原申请内容和截图，只覆盖明确选择的行政区划。

远程 MCP 需同步“每日任务优化”源码中的 `domp_area_matching.py`、`domp_automation.py`、`domp_submission_service.py`、`domp_offline_submission.py` 和 `domp_lifecycle_service.py`，然后重启 MCP。服务端仅允许原 SQL、原流程记录在尚未创建申请且区划选择失败的情况下续办；旧版已保存的“行政区划匹配不唯一”记录也支持这种续办。只更新微信端而未更新 MCP 时，会提示同步更新，不会创建新 request_id 绕过旧记录。

MCP 地址示例统一使用 `http://127.0.0.1:5222/mcp`。实际部署的内外网地址和令牌只填写在不受 Git 管理的本地 `config.yaml` 中，`token` 与服务器的 `api_token` 相同。调用由微信后端添加 `Authorization: Bearer <token>`；浏览器静态代码不保存固定令牌。新部署填入令牌后重新加载“AI 与 MCP 设置”或重启后端。缺失令牌会在请求前提示，401/403 会提示核对令牌；保存其他设置时留空会保留已有令牌。

“今年以来、本年度、年初至今”的问题平台统计按当年 1 月 1 日至查询当天计算，和“最近一年”区分。支持“运维平台问题数量”“运维平台单子数量”及中文/ISO 起止日期；明确的只读统计通过固定意图进入查询。本条日期优先于历史条件，MCP 调用优先发送具体起止日期，不能继承上一轮的 today 覆盖新日期。返回范围与请求不一致时停止生成表格，也不把错误结果存入会话。明确要求表格时，0 条结果仍发送含表头及日期范围的文件。

大范围统计使用平台原生的 `sortname=iid&sortorder=asc`，以唯一问题 ID 固定分页顺序，避免默认排序重复记录。只读列表或履历遇到 HTTP 410/会话过期时最多重新登录并读取一次；并发履历读取共享刷新后的认证，避免重复登录。填报、审核、执行请求不使用此读取恢复逻辑。

问题平台按日期范围查询的统计表增加“信息中心处理时间”，取完整需求履历中发起人“信息中心”的首次发起时间，不能用受理时间或当前受理人代替。详情读取使用最多 8 个独立只读会话；原列表总数和顺序保留，无信息中心记录、时间缺失及查询失败分别显示。微信文件名为 `2026-07-01至2026-09-30_问题平台提单统计.xlsx`；单日使用一个日期，全部历史使用“全部历史”。发送表格时使用 Hook 文档中的 `SendFileMsg_NoSrc` 显式 `fileName` 参数，防止显示为自动生成的 `PCWeChat_...`。履历查询允许较长的只读响应等待时间，不改变填报、审核、执行请求的超时规则。

## 文件传输助手中的本人任务

在前端“智能回复”点击“配置文件传输助手任务”，可以复制已有聊天的文本数据运维 Agent 配置并保存。配置仅归属当前登录账号，发送人强制绑定该账号；使用配置总开关和文本开关启停任务。向文件传输助手发送 `@空气`、唯一四位或五位单号和完整 SQL，会进入同一个风险检查、填报、审核、执行流程，结果回复到文件传输助手。没有 `@空气`、SQL 中的字面量艾特、其他账号或普通聊天不会进入此入口，规则和普通自定义任务不获得处理本人消息的权限。

五位单继续读取问题平台，四位线下单仍使用引用图片并确认识别出的城市；没有引用图片时用 SQL 图片兜底，并先要求本人输入城市或县区。本人明确输入并匹配系统支持项后直接填报、审核、执行，不再回复“是”。输入、确认图片识别结果和取消都必须再次 `@空气`，会话、防重请求和执行结果记录仍按登录账号、聊天和原发送人隔离。发送回复前记录其内容指纹，忽略对应的本人回调，避免提示中包含 `@空气` 时形成循环。

群消息的实际账号艾特检查只进行一次。回调缺少艾特元数据而正文含经缓存验证的本人昵称时，已通过的结果会传给消息过滤器；存在元数据时仍以实际 wxid 为准，不允许用正文覆盖其他账号的艾特目标。

## 四位线下单与引用图片

支持 `--xzsb-2750` 加完整 SQL 的线下单，包括微信引用图片后发送 SQL 的消息。其他发送人必须 `@登录账号（当前为 Aixed）`，登录账号本人必须 `@空气`。四位编号跳过问题平台，只在数据运维管理平台填报、审核、执行；五位编号继续读取旧需求。原 SQL、风险校验和防重标识保持一致，已有 Agent 配置的旧提示词会在运行时补充四位编号规则。

线下单附件优先使用当前消息直接引用的原图片；引用消息只有占位内容时按原图片 `svrid` 获取消息结构并调用 `DownFileorPic`，下载失败则停止并提示重试。只有没有引用图片时才生成完整 SQL PNG 作为兜底。聊天中的引用缩略图使用相同下载缓存，失败后可点击重新请求。

先读取截图中的“申请部门”，图像模型不可用时尝试 Hook OCR；行政区划以 `match_data_maintenance_city` 实时读取的平台完整支持项为准，支持市、县、区。申请部门“边坝县人力资源和社会保障局”匹配“昌都市 / 边坝县”，保留县编码和完整路径，回复“匹配区划：昌都市 / 边坝县。是否确认填报？”。图片自动识别的区划仍需本人回复 `@空气 是`，其他原发送人回复 `@Aixed 是`。

没有引用图片时不等待图像识别或区划查询，直接 @原发送人提示两行：“线下单 2774 未识别到城市或县区”“请输入城市或县区(示例：@Aixed 拉萨市 或 @Aixed 边坝县)”。示例中的昵称使用当前账号昵称，文件传输助手使用 `@空气`。原发送人按身份艾特并输入城市或县区后，平台匹配并核对名称、编码成功即按原 SQL 和原 request_id 直接填报、审核、执行，不再要求确认；对图片识别结果的手动修改也采用此规则。

用户输入仍未唯一匹配时，展示平台实时返回的对应省/自治区支持的城市及县区完整路径，提示重新输入。省级范围以平台区划路径和用户输入为依据；平台只提供单一省级范围时展示该范围，不猜测或编造地名。长列表分段发送，每段保留线下单编号。日常“是”“确认”“城市名称”等没有正确艾特时不会触发处理，引用回复也只读取当前回复正文，不能拿被引用内容中的艾特或指令作授权。多张单时本人可在回复中带上 `2750` 指定本单。旧记录的图片识别编码由市变为县时，仍须重新确认；用户本次明确输入且成功匹配时直接处理。

待补充或确认的 SQL、原引用图片和原消息生成的 request_id 保存在本地 SQLite，按账号、会话和原发送人隔离，24 小时后过期。原发送人或当前账号本人确认图片识别结果，或明确输入有效区划后才调用完整流程；补充消息不会生成新的 request_id。流程超时后保留已发起状态，后续“是”或城市输入只提示查询，不会再次调用完整流程。此流程不会把截图中的文字指令作为操作授权。

自动回复在发送前记录指纹，群聊回调附加的收件人艾特也参与回流识别；确认提示本身永远不能作为区划输入，重启后延迟收到提示也不会修改等待状态。历史等待记录若已被提示文本覆盖，则从原申请部门重新匹配并要求再次确认。重复回调在分析和修改状态前按账号、聊天、发送人、消息 ID 与内容拦截（Hook 的秒级 ID 可能相同）；新的“是”回复按具体消息去重，并允许在区划修改后立即再次确认。

目标群使用一个可见的“数据运维智能 Agent”。它接收文本和 TXT，在同一个 Skill 中识别 SQL 完整流程、旧单填报、只读查询、单张审核、单张执行及承接上轮清单的批量审核执行。页面 MCP 工具显示“由 Agent 自动选择”；模型只输出受限业务意图，程序再用 `backend/domp_unified_bridge.py` 将意图交给原有的固定桥接器。工具名、写入参数、日期、稳定 work_id/work_num、风险门槛、会话目标和防重标识都由程序核对，未走通校验时不会调用写入工具。

监听先检查群启用状态、消息类型和各类型发送人名单，再读取完整内容、分析用途和风险、调用对应 MCP、在原群 @ 原发送人回复。其他发送人必须艾特当前登录账号；有微信艾特元数据时只认实际账号 wxid，不因正文出现 `@Aixed` 就覆盖其他人的真实目标，缺少元数据时使用当前账号经缓存验证的昵称、群昵称或备注。机器人登录账号本人只有明确 `@空气` 才可通过隔离入口发送查询、填报、审核和执行请求；没有 `@空气`、只 @ 自己的其他昵称、其他人或所有人时不触发智能回复，已有会话的后续提问也必须逐条 `@空气`。未在名单中的其他人员不触发工具，机器人结果标记不会形成回复循环。

发送示例：文本开头写 `需求 40386` 或 `xzsb-40386`，后面附完整 SQL；也可发送 `需求40386.txt`，文件内容为完整 SQL，多条语句用分号分隔。不能从 SQL 主键猜需求编号。支持 UTF-8（含 BOM）、GB18030、UTF-16（带 BOM）；过大、无法解码或超过完整分析长度的文件会回复失败原因，不会截断后执行。

发送同一编号的 TXT 或聊天 SQL 后，同一发送人可在 24 小时内再发“提交填报运维单 41323，并审核执行”。程序承接该发送人在同一会话中最近的、文件名精确匹配 `41323.txt`（允许下载副本后缀 `(1)`）且可完整读取的 TXT，或前部明确写有同一唯一 5 位需求编号且包含完整 SQL 的聊天文本，将它直接送入完整 SQL 流程；不会先创建一张不含 SQL 的普通申请，也不会复用其他人的文件、其他编号或超过 24 小时的内容。没有匹配的 TXT 或聊天 SQL 时明确停止并提示先发送完整 SQL。

统一 Skill 的提示词见 `backend/domp_unified_bridge.py` 中的 `UNIFIED_PROMPT`。识别为 `sql_workflow` 后，程序才进入原 `process_data_maintenance` 固定流程。程序自行生成原文参数和稳定消息标识；模型输出用途和风险，高风险/未知/低置信度停止。风险阻断聚焦于无法解析或意图不明、无有效 WHERE/恒真条件导致整表修改、DDL/TRUNCATE/权限或过程语句、未绑定参数，以及同表同条件重复修改或关联语句业务编号明显错配等疑似复制错误。多条 UPDATE、未写 COMMIT、未知实际影响条数、敏感表/字段、待遇/状态/区划修改或可能一人多行本身只作为提示，不单独阻断。实际 SQL 结构与系统申请脚本还会在 MCP 端核对。

群消息或 TXT 中的 SQL 不再限制为最多 10 条；仍受全文 20000 字符限制。MCP 解析和提交层保留全部语句、原顺序及同一申请，逐条风险检查。业务请求前的 SQL 校验失败返回具体原因和“本次请求未填报、审核或执行”，不显示“结果待核对”；已经开始业务请求但响应不明的情况仍显示待核对并禁止重复执行。

审核、执行前对平台回读的 SQL 清单按规范化内容和重复次数核对，兼容平台返回顺序变化，避免原 SQL 未变却误报不一致。原文提交顺序和持久化防重指纹不变，实际修改内容、增删语句或重复次数变化仍阻断；旧流程记录无需删除或重新填报。

五位需求支持显式补充批次：客户可将 SQL 消息首行写成 `--- xzsb-42157-1`，后续使用 `-2`、`-3` 等正整数后缀。完整 `42157-1` 用于分析、填报、防重、查询、审核和执行，不得截成 `42157` 或 `1`；仅在读取旧需求说明和截图时使用基础编号 `42157`。重复编号且 SQL 不同时，本次不新增申请或执行业务，回复提示客户改用下一个未用批次并重新发送完整 SQL；相同 SQL 复用原流程结果并附重新填报提示。后缀只能由客户明确提供，程序不自动生成新申请、不覆盖原记录。四位线下编号保持原规则。

只询问问题平台单据数量且未要求明细、表格或处理时间时，程序传 `count_only=true`：普通数量直接读取平台按日期筛选后的总数，未完成数量仍完整扫描列表并应用既定状态排除规则，两者均不读取逐单履历。数量结果不生成空明细表；随后回复“整理为表格发我”会沿用原日期及筛选条件重新读取完整明细和处理时间。

只读查询超过 60 秒后，每 60 秒在原聊天回复一次实际进度，群聊只 @ 原发送人。查询服务按独立 `query_id` 暴露排队、扫描页数、单据数、处理时间补全数和最后进展时间；客户端只发送一次查询，并独立读取进度。进度获取异常时如实说明暂不可取，不重发统计；90 秒无新增结果时说明仍在等待平台响应。完成、失败或取消后停止进度回复，生成报表期间也保留进度提示。

文本开头或完整 SQL 末尾的 @ 昵称，先结合微信艾特元数据、群成员详细信息接口和群成员缓存确认是否为当前群成员；确认是群成员后才从送审文本中清除，随后将相同 SQL 内容交给模型和 MCP。不使用模型猜昵称；未知 @ 文本、SQL 参数、schema.table@dblink 数据库链接、字符串和 TXT 文件原文保持不变。风险检查按各语句的解析节点和令牌进行，字符串/注释中的 @ 不会误判成链接，也不会将另一条语句的参数风险套用到所有 SQL。

已有群可运行以下命令把五个数据运维 Skills 迁移成一个统一 Agent：

```powershell
backend\.venv\Scripts\python.exe scripts\configure_domp_skill.py --owner "登录账号wxid" --chat "目标群id@chatroom" --unify-agent
```

迁移会删除本群配置中的旧 SQL、查询、填报、审核和执行 Skill 项，创建文本和 TXT 两个消息类型下同名、同 `skill_id` 的统一 Skill；因此每个消息类型页面只显示一个 Agent。原配置先备份到 `backend/db/domp_skill_before_时间.json`，原发送人名单、群开关和 MCP 连接保留。重复运行命令只更新同一统一 Agent，不会重复创建。MCP 当前默认地址为 `http://127.0.0.1:5222/mcp`，可在 `config.yaml` 的 `mcp_connections` 中修改对应连接的 `url`，保留原 `id`；重启后端或打开「AI 与 MCP 设置」重新加载后生效。完整流程超时设置为 600 秒；数据运维助手必须运行且三个角色连接配置齐全。

返回需求编号、用途、风险、填报/审核/执行状态、逐条影响条数、合计、耗时和异常。0 保留、未知明确写“未知”，不使用分析回复冒充成功。长异常分段按顺序 @ 发送人回复。超时回复流程标识，使用查询接口核对，不能重新创建请求绕过防重。

页面 Skill 测试没有生产消息上下文，强制 `dry_run=true`，只分析不填报、审核、执行，也不发送微信。真实消息的业务写入由目标群和发送人名单授权；模拟测试均替换 MCP 和微信发送接口。

## 填报意图

“提交数据运维填报单 41356”“提交运维单 41356”“帮我提交数据运维单41356”由统一 Agent 识别为 `submit`，固定调用 `submit_data_maintenance(identifier="41356", force=false)`，对应桌面“一键读取填充并提交”：读取旧单、生成申请截图、匹配行政区划、保存提交并返回真实需求编号。无需 SQL，仅完成填报，不审批、不执行；含 SQL 的消息走完整 SQL 流程。允许原文本发送人名单及登录账号本人明确请求，本人使用隔离路径。单号必须来自当前消息，多个单号、编号不一致、否定或引用请求不提交；超时仅提示待核对，不自动重试。页面 Skill 测试只识别，不调用提交接口。每段回复带“数据运维填报结果”标记，防止回调循环。

## 查询意图

统一 Agent 识别到 `query` 后，实际 MCP 路由由程序限定在四个只读工具中：

- “查一下 41198 任务处理情况”“查一下 41198 处理情况”“xzsb-41198 谁在处理”：调用 `query_operation_ticket`，对应桌面“查询 → 综合查询”，返回旧系统当前状态、受理人、机构、处理履历和评论；转现场处理不代表已解决，履历受理标记为“未”时显示尚未受理。
- “查一下最近一个月问题平台运维单处理情况”“今天问题平台还有哪些未完成的单子”：调用 `query_operation_tickets`，按今天、昨天、最近一周、最近一个月、最近一年、全部历史或明确日期范围读取问题平台清单，后端一次性返回完整结果；也支持“最近一个月到上一周”这类组合范围，结束日按上周日计算。每条至少包含标识 ID、概述、状态、填报时间、受理人，并可保留问题 ID和受理单位。只要查询“未完成/未处理”，统一排除“完成待验证”“关闭(归档)”“验证不通过”“科长意见给出”“提出”，与时间范围无关。前端收到超过 10 条，或用户明确要求表格时，生成一份带列宽、行高、冻结表头和筛选的完整 `.xlsx` 表格文件发送，再发送状态数量等简短进度文字；其他情况返回文字明细。未明确平台时范围运维单默认问题平台。
- “帮我查一下 41123 执行情况”“41233 执行了吗，结果如何”“41233 执行了吗”“41178 影响多少条”“目前有所少待审核的需求”“现在有哪些待执行需求”：调用 `query_data_maintenance`，返回真实 SQL 执行状态、逐条影响条数、合计、耗时、完整异常，或当前待办数量与前 20 条清单。执行成功且明细完整、无异常时回复“异常详情：无”；执行失败但系统没有异常文本时明确说明未返回，未取得完整结果时异常为未知。
- “今天有没有代审核和待执行的单子”“昨天的还有没审核执行的”“上周有哪些待执行”：查询语境中的“代审核/代审批/代执行”兼容相应“待”字，分别调用两次只读 `query_data_maintenance`，同时回复两类真实数量和清单。支持今天、昨天、前天、本周、上周、本月、上月、最近 1–366 天和明确起止日期；待审核按申请时间筛选，待执行按审批通过时间筛选，日期范围包含首尾。某一类查询失败仅将该类标为未知，保留另一类结果；没有时间措辞时查询当前全部积压。普通陈述和写入指令不使用错字查询快捷路径。
- “41184 的执行详情发我看看”“把41184执行详情给我”“41184 SQL脚本发我看看”：仍调用只读 `query_data_maintenance`，在结果摘要中附逐条服务器 SQL 原文，不改写或再次执行。执行查询后接“详情呢/明细/SQL脚本呢”也可展示原文；会话仅保存不含 SQL 的结果摘要，长 SQL/异常按顺序分段 @ 原发送人，每段保留结果标记以防回调循环。
- “当前有多少待处理的任务”“今天分配了多少任务”“今天分配的任务详情”：调用 `query_task_processing`。待处理数量从新业务会话读取当前待处理清单，自动处理保持运行；今日分配来自本助手确认成功提交的 SQLite 持久化记录。回复包含编号、摘要、分配时间、指派人员、命中规则和真实结果，并说明启用时间及未保留历史/其他账号手工分配不在统计内。每页 20 条，可接“详情呢”“下一页”，翻页只承接同一发送人的已验证页码。

AI 识别意图，程序核对原消息编号；旧系统处理情况措辞强制走综合查询，不能误查 SQL 执行系统。未找到说明账号可见范围，同名多条需人工选择，读取失败不能冒充未找到或 0。查询不会启动自动派发或修改业务。

短查询即使没有拼对业务关键词也进入语义分析，例如“带审合的单子有多少”“有哪些代执形的单子”“查41184执形结过”；Agent 根据整句及有效会话理解同音、形近、漏字和口语，输出规范意图，程序继续固定只读工具。明显业务问题但含义不明确时提示补充，不调用工具；无关聊天不回复。单号不做模糊纠正，混淆的数字/字母必须由发送人确认，SQL 原文和写入授权不靠错字猜测。

原文本名单中的人员可查询，机器人登录账号的本人也可在该群直接发送查询。本人消息使用统一 Agent 的隔离入口，只允许当前消息明确表达的查询、填报、审核或执行意图；本人发送的 SQL 不自动进入完整流程，SQL 授权名单不变。机器人结果每段带对应结果标记，回调不会再次触发。普通聊天不会调用工具。

## 查询会话上下文

会话以“机器人登录微信账号 + 群聊/私聊 ID + 发送人微信 ID”隔离。同一人在不同群有独立会话，同一群内不同人不会继承彼此的单号；昵称变化不影响会话。每个会话从创建时起最多七天，持续聊天也不延长，到期清除旧上下文并在下一次明确查询时生成新 session_id。SQLite 表 `query_conversations` 保存最近十二轮已验证查询（每轮原问题和答复摘要各最多 1500 字），后端重启后仍可承接有效会话；不把整个群聊、TXT SQL 原文或完整需求中的个人信息当作上下文。

例如“有哪些待审批”后接“待执行呢”会重新查询当前待执行清单；“查41198任务处理情况”后接“那41199呢”会改查41199；“它的执行结果呢”沿用最近一轮明确编号。明确的新编号/类型优先，上一轮是数量查询时不猜单号；没有有效上下文时提示补充。明确 SQL 流程的结果只记录编号和结果摘要，也可接着查询执行结果，后续问题不会复用旧 SQL 进行业务修改。模型收到同一发送人的历史查询数据，所有状态/数量仍从当前 MCP 结果生成。

同一人的消息按接收顺序串行处理，其他人可并行查询。查询回复允许紧接着问和重复同样问法；重复回调仍按消息 ID 去重，机器人结果标记继续阻止循环。页面 Skill 测试不绑定生产会话。

## 审核意图

统一 Agent 的 `approve`/`approve_execute` 意图调用 `approve_data_maintenance`，处理“审核一下 41366 运维单”“审批数据运维单41366”等单张审核请求；“审核和执行一下运维单”“审核并执行 41366”会在审核明确通过后继续执行并返回逐条影响行数、耗时和异常。当前消息没有编号时，只承接同一发送人七天内最近一轮待审核查询中的唯一单据。程序在写入前重新读取待审核清单并核对稳定 work_id、work_num；同名多条、清单为空或变化时停止。查询、否定、未来计划和引用示例不会审核；“都审核执行一下”由 `approve_execute_all` 完整清单批量流程处理。

## 执行意图

统一 Agent 的 `execute` 意图调用 `execute_data_maintenance`。目标群原文本名单人员及登录账号本人可明确要求执行已有审批通过单据，本人使用隔离路径。可说“执行 41184”，或在同一发送人的上一轮待执行查询仅一条时说“执行下并告诉我结果”。程序保存最多 20 个已验证稳定编号；旧会话只认可程序标准答复里明确的一条工作编号，绝不拿最新清单中的另一条替代。清单为零/多条、会话过期、同名多条或目标不明时要求指定编号。执行结果提问仍走只读意图。

支持带称呼、@昵称及礼貌前缀的明确请求，例如“兄弟，帮我执行下 41184”“老师，麻烦把数据运维单 41184 执行一下”。入口按请求语句匹配而非要求整条消息以“执行”开头，登录账号本人也能进入隔离执行路径；否定、转述、未来计划及“执行了吗/帮我查执行结果”等只读问法不会发起执行。AI 确认动作，程序仍从当前原文核对唯一编号。

在刚查询待审核清单后发送“都审核执行一下”“全部审批并执行”，会承接同一发送人七天内最近一轮工具查询固定的完整目标，重新核对当前待审核状态后，逐单调用 `approve_data_maintenance` 和 `execute_data_maintenance`，并返回每单审核状态、逐条影响行数、耗时和异常。最多处理完整展示的 20 条；清单为空、超过范围、缺少稳定编号或任一目标已变化时，在写入前整体停止。单纯“都执行”或“都审核”、询问句、否定句不会触发。

执行前重新调用只读待执行清单，核对稳定 work_id、work_num 和审批状态；MCP 服务继续检查服务器内实际申请 SQL 的风险和持久化防重记录，仅允许执行一次。目标已移出清单只读取原单结果，不执行其他单据。响应异常只读核对结果，不重发执行。返回真实逐语句成功/失败、0 或未知影响条数、合计、耗时及完整异常，所有段在原群 @ 发送人，结果标记防止回调循环。页面 Skill 测试只定位单据，不执行或发送微信。

自动分配记录文件为数据运维助手目录中的 `task_assignments.local.sqlite3`，恢复旧运行日志只导入有真实成功提交时间的记录。
